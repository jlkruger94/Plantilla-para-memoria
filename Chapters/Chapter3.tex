El sistema embebido implementado en este trabajo consta de una PCB centralizadora, diseñada para integrar y gestionar todos los módulos de hardware. Esta arquitectura asegura la alimentación, adaptación y protección de todos sus componentes. El sistema completo abarca desde la adquisición de datos mediante sensores hasta las acciones sobre el entorno a través de actuadores. Además, se complementa con una interfaz de usuario móvil para el monitoreo y control remoto.

A continuación, se describen brevemente los bloques y su función.

\begin{itemize}
	\item Sensores: este bloque se encarga de la transducción de magnitudes físicas en señales eléctricas, lo que permite la digitalización de variables ambientales de interés para el control del cultivo.
	\item Adaptación de señal: los módulos de adaptación acondicionan las señales provenientes de los sensores. Para garantizar la correcta interpretación por parte de la unidad de microcontrolador o MCU (del inglés \textit{MicroController Unit}), ajustan los niveles de tensión y la relación señal-ruido a valores apropiados.
	\item MCU: el núcleo del sistema, basado en el chip ESP32, orquesta la comunicación y el control de todos los módulos. Provee la capacidad de procesamiento y la conectividad inalámbrica necesarias para la automatización del cultivo y la interacción con la aplicación móvil.
	\item Interfaces de salida: proporciona aislamiento galvánico y acondicionamiento de potencia para la activación de los actuadores, lo que asegura la protección del MCU y la correcta operación de los componentes de mayor potencia.
	\item Actuadores: los actuadores (ventiladores, bomba de irrigación, luces, resistencia calefactora) ejecutan las acciones de control y modifican las condiciones ambientales del cultivo según las necesidades.
	\item Aplicación móvil de usuario: desarrollada para facilitar la interacción con el sistema, la aplicación móvil permite el monitoreo en tiempo real de las condiciones del cultivo y el control remoto de los actuadores.
	\item Interfaz de servicio web: se implementó una interfaz para la transmisión de datos a un servicio web externo que permite el almacenamiento y análisis de información del cultivo. Esta funcionalidad se encuentra fuera del alcance principal de este trabajo.

\end{itemize}

\section{Arquitectura del firmware}

En la presente sección se aborda la arquitectura del firmware del microcontrolador.

\subsection{Patrones}

A continuación, se detallan los patrones de diseño arquitectónico utilizados.

\subsubsection{Arquitectura en capas}
Se adoptó un patrón de arquitectura en capas para estructurar el software desarrollado, lo que permitió una separación de funcionalidades clara mediante niveles de abstracción. Dicha metodología divide el sistema en niveles horizontales, cada uno con responsabilidades específicas y bien definidas, que facilita el desarrollo, la mantenibilidad y la escalabilidad del código.

A continuación, se enumeran las capas de abstracción que constituyen el firmware.

\begin{itemize}
	\item Capa de aplicación.
	\item Capa de sistema operativo.
	\item Capa de abstracción de hardware (HAL).
\end{itemize}


\subsubsection{Capa de abstracción de hardware}

Para facilitar la interacción con los diversos componentes de hardware y garantizar la portabilidad del código, se implementó una capa de abstracción basada en Espressif HAL (\textit{Hardware Abstraction Layer}). Integrada dentro del SDK de ESP-IDF, esta capa proporciona una interfaz uniforme para el control de los periféricos del ESP32, independientemente de las particularidades del hardware subyacente.

\subsubsection{Control ambiental}

El patrón de control ambiental se adoptó como estrategia arquitectónica para la capa de aplicación. El sistema embebido requirió la monitorización y modificación del entorno mediante sensores y actuadores. Este patrón permitió la estructuración de la lógica de control y facilitó la gestión de las interacciones entre los componentes de hardware y la implementación de los algoritmos de control.


\subsection{Componentes}

La capa de aplicación, figura \ref{fig:arq_bloques}, está constituida por los componentes de software encargados de gestionar cada una de las funcionalidades del sistema.
A continuación, se describe brevemente la funcionalidad de cada uno de estos componentes.

\begin{itemize}
	\item Monitor de temperatura: mide la temperatura de la solución nutritiva para garantizar que las plantas crezcan en un entorno térmicamente adecuado.
	\item Monitor de conductividad eléctrica (CE): evalúa la concentración de nutrientes presentes en la solución hidropónica.
	\item Monitor de nivel: monitorea que el nivel de solución nutritiva en el sistema no caiga por debajo de un valor determinado.
	\item Monitor de pH: mide el nivel de acidez de la solución nutritiva, lo que ayuda a mantener el pH dentro del rango óptimo para el cultivo.
	\item Monitor de humedad del sustrato: mide el contenido de humedad en el sustrato del cultivo.
	\item Monitor de luz: mide la cantidad de luz disponible en el entorno a través de un sensor.
	\item Servidor web embebido: el servidor web embebido permite la comunicación con el sistema de control del cultivo a través de la red. Este servidor permite monitorear, configurar y controlar el sistema desde cualquier dispositivo con acceso a la red.
	\item Control de ciclo de luz: este módulo se encarga de gestionar el ciclo de iluminación del cultivo. La configuración de dicho ciclo se realiza por medio de la interfaz de usuario.
	\item Control de ciclo de oxigenación/ventilación: este componente activa y desactiva el flujo de aire en el sistema de cultivo según la configuración del usuario.
	\item Control de hidratación: gestiona el riego, activa la bomba de agua y ajusta los niveles de humedad del sustrato según las mediciones del sensor de humedad. Esto asegura la cantidad adecuada de agua para el desarrollo de las plantas.
	\item Administrador: es el componente encargado de la centralización y validación global de los datos suministrados por los demás módulos de software.
\end{itemize}

\section{Desarrollo del software}

Para facilitar la escalabilidad de la aplicación, se implementó una tarea de FreeRTOS para cada componente del firmware. Esta arquitectura modular permite modificar cada elemento de forma independiente, sin afectar al resto del sistema.

\subsection{Gestión de la comunicación entre tareas}
La comunicación entre tareas se gestiona mediante un patrón de publicación/suscripción con múltiples canales, que utiliza colas como buffers para el intercambio de datos. Esta arquitectura desacopla los productores de información (monitores) de los consumidores (controladores y administrador), lo que garantiza la integridad de los datos y la estabilidad del sistema al evitar condiciones de carrera.

\subsection{Gestión de prioridades}
Se asignaron diferentes niveles de prioridad a las tareas según su criticidad. Las de monitoreo se configuraron con prioridad intermedia, mientras que las de control y administración recibieron mayor prioridad para asegurar tiempos de respuesta adecuados. El servidor, al depender de la interacción del usuario, fue asignado con prioridad alta.

Los monitores funcionan como tareas productoras que obtienen datos del entorno mediante sensores y los publican en estructuras compartidas. Los controladores actúan como tareas consumidoras que toman decisiones basadas en estos datos y accionan los actuadores correspondientes. La tarea de administrador, también consumidora, coordina el funcionamiento general del sistema y gestiona configuraciones.

\subsection{Controladores de dispositivos}
Se desarrollaron controladores de dispositivos (\textit{device drivers}) dedicados a gestionar directamente las unidades de hardware, mediante la abstracción de las operaciones de bajo nivel necesarias para interactuar con sensores y actuadores.

\subsection{Gestión de fallos}
El sistema incorpora mecanismos de detección y manejo de fallos a nivel de hardware y software. Cada tarea cuenta con rutinas de supervisión que identifican comportamientos anómalos o pérdida de respuesta de los dispositivos.

En caso de error, se activan procedimientos de contingencia que buscan restablecer el funcionamiento sin alterar la estabilidad general. Por ejemplo, si un sensor deja de enviar datos válidos durante un tiempo determinado, se genera una alerta que es registrada y comunicada al usuario. Si un actuador no responde tras múltiples intentos, se desactiva su uso y se notifica mediante una bandera de estado.

Además, se implementó un mecanismo de \textit{watchdog} que reinicia automáticamente el microcontrolador en caso de bloqueo o error crítico no recuperable. La configuración del usuario se almacena en memoria no volátil (NVS) por medio de un sistema de archivos, lo que permite la recuperación de parámetros tras cortes de energía.

\subsection{Servidor embebido y API REST}
El sistema cuenta con un servidor embebido HTTP alojado en la ESP32 que expone una API REST para la interacción con el usuario. Esta permite el monitoreo del estado del cultivo, la consulta de valores de sensores en tiempo real, y la ejecución de acciones como el encendido manual de actuadores o la configuración del dispositivo.

El servidor opera concurrentemente con el resto de las tareas gracias a la arquitectura multitarea de FreeRTOS, y cuenta con un sistema básico de autenticación por usuario y contraseña.

La API REST atiende peticiones HTTP desde navegadores y la aplicación \textit{Progressive Web Application} (PWA) desarrollada en React, que se distribuye mediante un servidor Docker desplegado en una Raspberry Pi 4 Model B.

Las operaciones principales incluyen:
\begin{itemize}
    \item Lectura de datos ambientales (temperatura, humedad, pH, EC).
    \item Consulta del estado de actuadores (iluminación, bomba, ventilación).
    \item Configuración de parámetros y umbrales de alerta.
    \item Activación manual o automática de funciones del sistema.
    \item Acceso a registros de eventos y errores.
\end{itemize}

El firmware mantiene una estructura centralizada de datos que se sincroniza con la aplicación móvil a través de sesiones HTTP válidas, asegurando que el usuario visualice información actualizada del cultivo.

\subsection{Lógica de negocio}
Al encender el sistema por primera vez, se configura automáticamente el acceso Wi-Fi mediante el protocolo \textit{Wi-Fi Protected Setup} (WPS). El dispositivo espera la activación del botón WPS del router para obtener las credenciales, que se almacenan localmente para futuros reinicios. Si la conexión falla, el proceso se reinicia automáticamente.

Una vez establecida la conexión, se inicia el servidor embebido y se habilita la interacción con la aplicación móvil.

\subsection{Estructura del código}
La arquitectura sigue el patrón modular con módulos de software que ejecutan tareas de forma ordenada. El ciclo comienza en \texttt{main.c} con la inicialización del sistema a través del componente \texttt{Administrator}, como se detalla en la figura \ref{fig:flujo:sistema}.

\subsubsection*{Inicialización del sistema}
La función \texttt{app\_main()} crea la tarea \texttt{administrator\_callback} con alta prioridad, que actúa como un coordinador general que gestiona la interacción entre módulos y subsistemas.

Durante la inicialización, el \texttt{Administrator} configura el pool de memoria, inicializa el sistema de archivos, establece la conectividad Wi-Fi e inicia el servidor web.

\subsubsection*{Configuración de hora y alarmas}
El sistema incorpora un módulo \textit{Real Time Clock} (RTC) que garantiza precisión temporal durante interrupciones de energía. Además, inicializa un sistema de alarmas con niveles de severidad variables y persiste los mensajes en archivo para evitar pérdida de información tras reinicios.

\subsubsection*{Creación de monitores de sensores}
Se crean seis tareas independientes de monitoreo para sensores específicos del sistema hidropónico, gestionadas por sus respectivos \textit{device drivers}:

\begin{itemize}
    \item \texttt{temperature\_monitor}: muestrea la temperatura (DS18B20).
    \item \texttt{moisture\_monitor}: mide la humedad del sustrato (sensor capacitivo v2.0).
    \item \texttt{light\_monitor}: muestrea la iluminancia (BH1750).
    \item \texttt{solution\_level\_monitor}: sensor de nivel de solución.
    \item \texttt{pH\_monitor}: mide pH (módulo PH-4502C).
    \item \texttt{EC\_monitor}: mide conductividad eléctrica y concentración de nutrientes.
\end{itemize}

Cada monitor es una tarea independiente que realiza lecturas cada segundo y publica datos hacia el administrador.

\subsubsection*{Inicialización de controladores de actuadores}
Paralelamente, se crean tres controladores como tareas independientes:

\begin{itemize}
    \item \texttt{moisture\_controller}: administra riego automático por nivel o intervalo.
    \item \texttt{light\_controller}: controla luces según ciclo diurno para interiores.
    \item \texttt{fan\_controller}: regula ventilación y circulación de aire.
\end{itemize}

Estos controladores operan de forma autónoma según la configuración establecida previamente por el usuario, y también pueden recibir órdenes del sistema para activar o desactivar dispositivos.

\subsubsection*{Mecanismo de comunicación Pub/Sub}
El sistema utiliza un mecanismo de \textit{publish/subscribe} que permite interacción desacoplada entre componentes. Los sensores publican mediciones en tópicos específicos, mientras los controladores se suscriben a comandos de actuación. El \texttt{Administrator} supervisa el flujo completo de información.

\subsubsection*{Bucle principal de control}
Una vez inicializado, el \texttt{Administrator} ejecuta un bucle principal de un segundo que realiza las funciones detalladas en la figura \ref{fig:flujo:sistema}:

\begin{itemize}
    \item Lee datos publicados por sensores.
    \item Evalúa condiciones de alarma mediante comparación con umbrales configurados.
    \item Actualiza la API REST con información en tiempo real.
    \item Procesa modificaciones de configuración del usuario.
\end{itemize}

\subsubsection*{Arquitectura de tareas paralelas}
El diseño basado en tareas paralelas permite a sensores y controladores operar independientemente bajo supervisión del \texttt{Administrator}, como se ilustra en la figura \ref{fig:flujo:sistema}. Esta estructura evita cuellos de botella y asegura respuesta rápida, lo que resulta en un programa robusto, escalable y mantenible.

\subsection{Gestion de la configuración}
Al iniciar, el sistema crea un archivo \texttt{config.json} en la memoria flash. Este archivo se genera con valores por defecto, ya que el usuario aún no ha configurado el dispositivo. Para su creación y almacenamiento se utilizan las bibliotecas \texttt{json\_static.h} y \texttt{fs.h}, respectivamente. Simultáneamente, se inicializa en memoria RAM la estructura \texttt{g\_current\_config}, que mantiene la configuración durante toda la ejecución del programa. Esta estructura solo se actualiza mediante la interacción del usuario a través de la API REST, al utilizar el endpoint \texttt{/config} con el método POST.

Cuando se recibe una nueva configuración, se actualiza la variable global definida en \texttt{hydro\_rest.c}. Inmediatamente, se envía un mensaje a través del tópico \texttt{u\_config} con un indicador que especifica qué módulo fue actualizado. Esto permite al administrador actualizar \texttt{config.json} y propagar la configuración al controlador correspondiente.

\subsection{Diseño electrónico}
% Explicar cómo se diseñaron las placas, esquemas, y conexiones eléctricas.
El diseño electrónico se realizó en base a una arquitectura modular. Cada subsistema se desarrolló con su propio esquema eléctrico para facilitar el mantenimiento y la escalabilidad.  
Se emplearon herramientas de diseño asistido por computadora (CAD) como \textit{KiCad} o \textit{Altium Designer} para la creación de los circuitos impresos (PCB).

\subsubsection*{Módulo de control principal}
% Describir el microcontrolador, sus interfaces y funciones.
El núcleo del sistema está basado en el microcontrolador \texttt{ESP32}, que proporciona conectividad Wi-Fi, múltiples interfaces de comunicación (UART, I2C, SPI) y suficiente capacidad de procesamiento para la ejecución de tareas en tiempo real.

\subsubsection*{Sensores}
% Describir tipos, rangos y conexión de sensores.
El sistema integra sensores de temperatura, humedad, pH, conductividad eléctrica y nivel de solución nutritiva. Cada sensor se conecta mediante buses digitales o entradas analógicas, según corresponda.  
Las señales analógicas son acondicionadas mediante circuitos de adaptación de nivel y filtrado para mejorar la precisión de lectura.

\subsubsection*{Actuadores}
% Describir bombas, luces, ventiladores, etc.
Los actuadores incluyen bombas de agua, luces de crecimiento y ventiladores. Su control se realiza mediante transistores MOSFET y relevadores de estado sólido, que garantizan una conmutación eficiente y segura.

\subsection{Sistema de alimentación}
% Explicar fuentes, reguladores y protecciones eléctricas.
El sistema cuenta con una fuente de alimentación conmutada de 12\,V, de la cual se derivan los niveles de 5\,V y 3.3\,V mediante reguladores lineales y DC-DC.  
Se incorporaron fusibles de protección, diodos de polaridad inversa y condensadores de desacoplo para garantizar la estabilidad del sistema.

\subsection{Diseño del PCB y ensamblaje}
% Describir el proceso de diseño, fabricación y ensamblaje del circuito.
El diseño del PCB prioriza la separación de señales de potencia y control, reduciendo interferencias electromagnéticas.  
Las pistas críticas fueron dimensionadas de acuerdo con las corrientes máximas esperadas. El ensamblaje se realizó de manera manual utilizando componentes montados en superficie (SMD) y de orificio pasante (TH).

\subsection{Pruebas y validación}
% Describir pruebas de continuidad, consumo, funcionamiento de sensores, etc.
Se realizaron pruebas eléctricas de continuidad y verificación de polaridades antes de alimentar el circuito.  
Posteriormente, se llevaron a cabo pruebas funcionales para validar el correcto funcionamiento de los sensores, actuadores y módulos de comunicación.  
Los resultados confirmaron la estabilidad del sistema bajo condiciones normales de operación.

\subsection{Consideraciones de seguridad y mantenimiento}
% Explicar protecciones, aislamiento, mantenimiento preventivo, etc.
El diseño incluye aislamiento galvánico en las líneas de control de los actuadores, protecciones contra sobrecorriente y sobretemperatura, y puntos de fácil acceso para mantenimiento.  
Estas medidas aumentan la vida útil del sistema y reducen el riesgo de fallos eléctricos.

\section{Selección y calibración de sensores}

Esta sección describe los criterios de selección y el proceso de calibración de los sensores utilizados en el sistema \textit{HydroGrow}. El objetivo es garantizar mediciones precisas y confiables de las variables críticas del entorno hidropónico.

\subsection{Selección de sensores}
% Explicar criterios de selección: precisión, rango, costo, disponibilidad, comunicación, etc.
La selección de los sensores se realizó considerando precisión, estabilidad, compatibilidad eléctrica y facilidad de integración con el microcontrolador \texttt{ESP32}.  
Los sensores elegidos fueron:

\begin{itemize}
    \item \textbf{Temperatura:} Sensor digital DS18B20, con rango de medición de $-55$\,°C a $+125$\,°C y resolución de 12 bits.
    \item \textbf{Humedad del sustrato:} Sensor capacitivo analógico, resistente a la corrosión y con respuesta lineal en el rango de 0–100\,\%.
    \item \textbf{pH:} Sonda analógica con amplificador de alta impedancia, calibrable mediante buffer estándar de pH 4, 7 y 10.
    \item \textbf{Conductividad eléctrica (EC):} Sensor tipo electrodo doble, compatible con soluciones nutritivas de 0.1 a 20\,mS/cm.
    \item \textbf{Nivel de solución:} Sensor ultrasónico con salida analógica, no intrusivo y resistente al ambiente húmedo.
    \item \textbf{Luminosidad:} Sensor digital BH1750, con rango de 1 a 65\,535\,lx, conectado por bus I2C.
\end{itemize}

\subsection{Calibración de sensores}
% Describir procedimientos generales o específicos de calibración.
Cada sensor fue sometido a un proceso de calibración inicial para asegurar lecturas precisas:

\begin{itemize}
    \item Los sensores de pH y EC se calibraron con soluciones patrón de referencia, registrando los valores de compensación en el archivo \texttt{config.json}.
    \item Los sensores de temperatura y humedad se verificaron frente a instrumentos certificados, aplicando correcciones lineales cuando fue necesario.
    \item El sensor de luminosidad se ajustó mediante comparación con un luxómetro de laboratorio.
    \item El sensor de nivel se calibró mediante mediciones en puntos de referencia físicos (mínimo, medio y máximo).
\end{itemize}

Las constantes de calibración se almacenan en memoria flash y se cargan durante el arranque del sistema. Esto permite conservar los ajustes incluso después de un reinicio y garantiza la coherencia en las mediciones a lo largo del tiempo.

\section{Interfaz gráfica}

Esta sección describe el diseño, estructura y funcionamiento de la interfaz gráfica del sistema \textit{HydroGrow}. El objetivo principal de la interfaz es proporcionar al usuario una visualización clara y en tiempo real de los parámetros del cultivo, además de ofrecer herramientas intuitivas para el control y la configuración del sistema.

\subsection{Arquitectura del sistema de interfaz}
% Describir la estructura general de la interfaz (cliente-servidor, arquitectura REST, etc.)
La interfaz se basa en una arquitectura cliente-servidor. El servidor web embebido en el \texttt{ESP32} expone una API REST que permite la comunicación entre el hardware y la aplicación móvil o el navegador web del usuario.  
El cliente se implementa como una aplicación web ligera desarrollada en \textit{HTML5}, \textit{CSS3} y \textit{JavaScript}, optimizada para dispositivos móviles y de escritorio.

\subsection{Diseño de la interfaz de usuario}
% Describir la disposición visual, estilo, principios de diseño y usabilidad.
El diseño se desarrolló siguiendo los principios de usabilidad y consistencia visual. Se empleó un esquema de colores contrastantes que facilita la lectura de valores críticos y una disposición modular basada en tarjetas o paneles.  
Cada sección agrupa información relacionada, lo que simplifica la navegación y permite una rápida identificación de los estados del sistema.

\subsubsection*{Panel de monitoreo}
% Explicar qué muestra y cómo se actualiza.
El panel principal presenta en tiempo real los valores de los sensores de temperatura, humedad, pH, conductividad eléctrica y nivel de solución.  
Las mediciones se actualizan mediante peticiones periódicas a la API REST, lo que garantiza una visualización fluida sin recargar la página.

\subsubsection*{Panel de control}

En esta sección, el usuario puede activar o desactivar manualmente los actuadores (bomba de riego, iluminación, ventilación) y ajustar parámetros de operación.  
Las acciones se transmiten al servidor mediante solicitudes \texttt{POST} a los endpoints definidos en el módulo de control.

\subsubsection*{Panel de configuración}
% Explicar cómo se gestionan los parámetros del sistema.
El panel de configuración permite modificar umbrales de alarma, intervalos de muestreo y credenciales de red.  
Una vez confirmados los cambios, el sistema actualiza el archivo \texttt{config.json} en memoria flash y propaga los nuevos valores a los controladores correspondientes.

\subsection{Comunicación con la API REST}
% Explicar endpoints y métodos principales.
La comunicación entre la interfaz y el sistema embebido se realiza a través de una API REST que sigue una estructura estandarizada.  
Los principales endpoints son:

\begin{itemize}
    \item \texttt{GET /status}: obtiene los valores actuales de sensores y estado del sistema.
    \item \texttt{POST /config}: actualiza la configuración general.
    \item \texttt{POST /control}: envía comandos directos a los actuadores.
    \item \texttt{GET /alarms}: consulta el registro de alarmas activas o históricas.
\end{itemize}

Cada solicitud y respuesta se maneja en formato \texttt{JSON}, lo que facilita la integración con otras plataformas o aplicaciones externas.

\subsection{Pruebas de usabilidad}

Se realizaron pruebas de usabilidad con un grupo de usuarios para evaluar la claridad de la información y la facilidad de navegación.  
Los resultados demostraron que la estructura modular reduce el tiempo de acceso a la información y permite la configuración completa del sistema sin requerir conocimientos técnicos avanzados.

\subsection{Compatibilidad y optimización}
% Mencionar compatibilidad con dispositivos y rendimiento.
La interfaz es completamente responsiva y se adapta a diferentes tamaños de pantalla. Se optimizó el rendimiento mediante la reducción de recursos estáticos, compresión \texttt{gzip} y almacenamiento en caché de datos locales.  
Estas optimizaciones minimizan el tiempo de carga y mejoran la experiencia del usuario incluso en conexiones inalámbricas inestables.

\subsection{Seguridad y autenticación}
% Describir autenticación de usuarios, cifrado, etc.
Para garantizar la seguridad de las comunicaciones, la API REST implementa un mecanismo de autenticación por token y el intercambio de datos se cifra mediante HTTPS.  
Además, se incorporaron restricciones de acceso por rol para prevenir modificaciones no autorizadas en la configuración del sistema.
