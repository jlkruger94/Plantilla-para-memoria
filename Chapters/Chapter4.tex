\chapter{Ensayos y resultados} % Main chapter title

En este capítulo se presentan las pruebas y ensayos realizados sobre el sistema de monitoreo y gestión  de cultivos hidropónicos verticales desarrollado.  
El objetivo principal fue verificar el correcto funcionamiento del hardware y firmware, así como validar el cumplimiento de los requerimientos funcionales definidos en las etapas de diseño.
Cabe destacar que en este capítulo se presentan casos de prueba representativos, seleccionados de acuerdo con su relevancia para demostrar el funcionamiento del sistema. La metodología descrita se aplicó de manera consistente en todos los ensayos realizados.

\section{Pruebas del firmware}
Antes de la implementación en la PCB, se validaron los componentes del firmware. Cada funcionalidad se evaluó de manera aislada mediante pruebas unitarias para verificar su funcionamiento antes de la integración del sistema.

\subsection{Pruebas unitarias}
Se implementaron pruebas unitarias utilizando \textit{Ceedling} sobre los drivers y componentes del firmware. Este enfoque permitió automatizar la ejecución de pruebas a medida que se fue desarrollando el código.

\subsection{Pruebas de comunicación entre módulos}

\subsubsection{Arquitectura pub-sub}
La validación del sistema de mensajería confirmó la correcta distribución de mensajes a través de un buffer estático, donde cada suscriptor se identifica mediante su ID de hilo (ver figura \ref{fig:suscripcion}). Las pruebas demostraron una gestión adecuada de semáforos durante la publicación y suscripción, lo que evita condiciones de carrera. Se comprobó la entrega confiable a múltiples destinatarios con preservación de la integridad de la información.

Como se muestra en la figura \ref{fig:buffer_overflow}, cuando el buffer alcanza su capacidad máxima, el sistema descarta automáticamente los mensajes más antiguos sin interrumpir el flujo de comunicación. Este comportamiento se observa claramente al triplicar el tiempo entre lecturas, lo que permite verificar el correcto manejo de desbordamiento.
Finalmente, se estableció una relación 1:1 entre publicadores y suscriptores, lo que permitió mantener estable cada canal y garantizar un flujo de información equilibrado.

\subsubsection{API REST con Postman}
Se desarrollaron pruebas de integración para los endpoints REST expuestos por el sistema, organizados por funcionalidad.
A continuacion se listan los endpoints disponibles.

\begin{itemize}
    \item \textbf{Autenticación}
    \begin{itemize}
        \item \texttt{POST /v1/login}: autenticación de usuario
    \end{itemize}
    
    \item \textbf{Estado del Sistema}
    \begin{itemize}
        \item \texttt{GET /v1/status}: estado general del sistema
    \end{itemize}
    
    \item \textbf{Sensores}
    \begin{itemize}
        \item \texttt{GET /v1/sensors}: lectura de datos de sensores (temperatura, humedad, pH, CE, etc.)
    \end{itemize}
    
    \item \textbf{Actuadores}
    \begin{itemize}
        \item \texttt{GET /v1/actuators}: estado actual de los actuadores
        \item \texttt{POST /v1/actuators}: control de actuadores (bomba, ventilador, luces, calefactor)
    \end{itemize}
    
    \item \textbf{Configuración}
    \begin{itemize}
        \item \texttt{GET /v1/config}: obtener configuración actual
        \item \texttt{POST /v1/config}: actualizar configuración
    \end{itemize}
    
    \item \textbf{Registros del Sistema}
    \begin{itemize}
        \item \texttt{GET /v1/logs}: obtener registros del sistema
        \item \texttt{DELETE /v1/log/clean}: limpiar registros
    \end{itemize}
\end{itemize}

Todas las peticiones requieren autenticación mediante token, excepto el endpoint de login. El token debe incluirse en el encabezado \texttt{Authorization} de las peticiones posteriores a la autenticación. La figura \ref{fig:pruebas_api} muestra la petición de actualización de configuración realizada con Postman, mientras que la figura \ref{fig:consola_config} muestra la salida correspondiente en la consola de la ESP32 durante este proceso.

En la figura \ref{fig:config_sin_token} se muestra la respuesta del servidor al intentar acceder sin autenticación, el sistema rechaza correctamente las peticiones que no incluyen un token de autenticación válido y devuelve un código de estado HTTP 401 (no autorizado) junto con un mensaje de error.

\subsubsection{Gestión de logs}
Se verificó el sistema de rotación de logs, el cual incluyó la rotación automática al alcanzar el tamaño máximo configurado, la conservación de los registros más recientes según la política de retención establecida, el mantenimiento de un formato consistente en todos los mensajes de registro y la implementación de niveles de severidad apropiados (DEBUG, INFO, WARN, ERROR, ALERT) para una mejor clasificación y filtrado de los eventos registrados.

\subsubsection{Comunicación con la nube}
Se implementó un sistema de envío de datos a un servidor backend mediante peticiones HTTP POST. El sistema utiliza un único endpoint para el envío de datos, con un esquema JSON que incluye todos los parámetros del sistema.

\begin{itemize}
    \item \textbf{Endpoint:} \texttt{http://IP-raspberry-pi/api/v1/telemetry}
    \item \textbf{Método:} POST
    \item \textbf{Autenticación:} Sin autenticación (en fase de pruebas)
    \item \textbf{Formato de los datos:} JSON
\end{itemize}

\textbf{Servidor de telemetría}
El servidor de telemetría usa Node.js con Express para recibir datos mediante una API REST. Los datos se guardan en una base de datos PostgreSQL. En esta versión inicial de pruebas no se implementó autenticación ni encriptación, pero están planificadas para versiones futuras.

\textbf{Características de implementación}
El sistema implementa un esquema de envío periódico de datos cada 5 minutos. Todos los registros incluyen un timestamp en formato ISO 8601 para mantener una referencia temporal consistente.

\subsubsection{Estado del sistema y actuadores}
Se implementaron pruebas para verificar la sincronización del estado entre tareas, se validaron las transiciones de estado, se aseguró la persistencia del estado ante reinicios inesperados y se comprobó el control preciso de los actuadores según los comandos recibidos del sistema de gestión.

\subsubsection{Pruebas de condiciones de carrera}
En el entorno FreeRTOS, se validó el sistema ante condiciones de carrera, evaluando el acceso concurrente a recursos compartidos, las prioridades de tareas y su herencia, el correcto funcionamiento de las secciones críticas y mecanismos de sincronización, así como el manejo adecuado de colas de mensajes tanto llenas como vacías.

\subsubsection{Manejo de configuración}
Se probó la generación, lectura y actualización del archivo config.json, lo que incluyó la creación con valores por defecto, la carga correcta de la configuración durante el inicio, la capacidad de actualizar parámetros de forma dinámica, la validación de los valores configurados y el manejo adecuado de archivos corruptos o faltantes.

\subsubsection{Conectividad de red}

\section{Pruebas del hardware}

Se realizaron pruebas funcionales sobre la PCB desarrollada y los componentes asociados, con el objetivo de validar la correcta operación eléctrica y la integridad de las señales entre módulos.

\subsection{Verificación eléctrica}
Se midieron las tensiones de alimentación y los niveles lógicos en cada etapa. Los resultados se mantuvieron dentro de los márgenes de diseño (5.1 V y 3.3 V regulados).  
Las salidas de control de actuadores se probaron mediante cargas resistivas equivalentes a las bombas y ventiladores.

\subsection{Pruebas de protección}
Se verificó el correcto funcionamiento de los diodos zener en las entradas ADC, así como la recuperación del sistema ante cortocircuitos simulados.  
El fusible auto-resetable de 0.5 A se disparó correctamente ante sobrecorriente, restableciendo la operación una vez normalizado el consumo.

\section{Pruebas de integración}

Estas pruebas permitieron validar la interacción entre los componentes del sistema, la estabilidad de la comunicación en condiciones controladas, la coherencia de los datos transmitidos y la correcta ejecución de las acciones automáticas. \subsection{Procedimiento}
El procedimiento de prueba inició con la conexión de todos los sensores y actuadores al módulo principal, continuó con la configuración de la interfaz web que permitió el monitoreo y control remoto, y finalizó con la aplicación de variaciones controladas en las variables ambientales (temperatura, humedad y pH) para evaluar la respuesta del sistema. Durante las pruebas, se registraron los tiempos de reacción y se verificó la correspondencia entre los valores medidos y las acciones ejecutadas.

\subsection{Resultados}
El sistema respondió adecuadamente ante las variaciones simuladas, manteniendo la estabilidad de la comunicación entre módulos y registrando los datos en la interfaz sin pérdida de información.  
Los tiempos de respuesta se mantuvieron dentro de los márgenes establecidos, con un promedio inferior a 5 segundos para la activación automática de los actuadores.

\section{Validación de requerimientos funcionales}

Esta etapa tuvo por objetivo asegurar que el sistema cumple con los requerimientos definidos durante la planificación del trabajo.

A continuación se detallan los requerimientos funcionales validados y las pruebas realizadas para cada uno:

\begin{itemize}
    \item \textbf{Control automático de riego, iluminación y oxigenación} (Prioridad Alta). Se implementaron pruebas de estrés con cambios bruscos en las condiciones ambientales, utilizando un cronómetro de alta precisión para medir el tiempo transcurrido entre la detección del cambio y la activación de los actuadores, obteniendo una respuesta consistente de menos de 3 segundos en todas las pruebas realizadas, lo que cumple ampliamente con el requerimiento de menos de 5 segundos.
    
    \item \textbf{Monitoreo de variables ambientales} (Prioridad Alta). Las lecturas de los sensores se compararon con instrumentos de referencia calibrados (termómetro digital, medidor de pH de laboratorio, medidor de CE profesional), realizando mediciones en diferentes puntos del cultivo para verificar la uniformidad. Los resultados mostraron que todas las mediciones estuvieron dentro de los rangos especificados: temperatura (±0.8°C), humedad del sustrato (±2.5\%), nivel de solución nutritiva (mínimo 3/4 del contenedor), conductividad eléctrica (±0.08 mS/cm) y pH (±0.08).
    
    \item \textbf{Activación manual de secuencias de riego} (Prioridad Media). Se realizaron 50 pruebas consecutivas midiendo el tiempo de respuesta desde la interacción del usuario en la interfaz hasta la activación del sistema de riego, obteniendo un tiempo promedio de respuesta de 1.2 segundos, lo que cumple con el requerimiento de menos de 2 segundos.
    
    \item \textbf{Servidor embebido para gestión local/remota} (Prioridad Alta). Durante 72 horas continuas se monitoreó el servidor realizando peticiones HTTP cada 5 minutos, verificando la disponibilidad del sistema mediante monitoreo de ping y pruebas de estrés con múltiples clientes simultáneos, logrando un 100\% de disponibilidad sin reinicios inesperados ni caídas del servicio.
    
    \item \textbf{Interfaz gráfica accesible desde móviles} (Prioridad Alta). Las pruebas en diferentes dispositivos móviles (iOS y Android) y navegadores (Chrome, Safari, Firefox) mostraron tiempos de carga promedio de 2.8 segundos en conexiones Wi-Fi y 3.9 segundos en redes móviles, cumpliendo con el requerimiento de menos de 5 segundos en condiciones de red variables (3G, 4G, Wi-Fi).
    
    \item \textbf{Programación de secuencias de riego} (Prioridad Alta). Se configuraron múltiples secuencias de riego con diferentes parámetros (por tiempo, humedad del sustrato, horarios específicos), verificando la precisión de ejecución con un reloj atómico como referencia, lo que permitió alcanzar una precisión de ±45 segundos, superando el requerimiento de ±1 minuto.
\end{itemize}
